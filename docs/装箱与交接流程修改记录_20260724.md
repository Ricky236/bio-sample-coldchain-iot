# 装箱与交接流程修改记录

日期：2026-07-24

## 一、问题说明

原“发出交接”页面底部显示“交出人人脸已通过，等待接收方确认”，容易被理解为装箱操作尚未完成，同时没有清楚说明下一步应由谁操作。

系统真实业务规则如下：

1. 发货方创建运单并绑定设备。
2. 完成首条监测预检后，运单状态变为 `pending_handoff`，此时即代表装箱完成。
3. 系统为该次交接生成一次性动态二维码。
4. 指定承运人使用自己的账号扫描二维码。
5. 承运人完成本人人脸检测。
6. 承运人确认接收后，责任转移，运单状态变为 `in_transit`。

装箱不是在人脸页面再次点击按钮完成的。设备绑定和首条预检通过就是装箱完成的业务凭证。

## 二、本次前端改动

修改文件：

- `miniprogram/src/pages/handoff/index.vue`

完成内容：

- 新增“装箱已完成”状态卡，明确显示设备绑定与首条监测预检已经通过。
- 明确展示下一步为“承运人扫码接收”。
- 发货方底部按钮按流程显示：
  - 装箱已完成，请让承运人扫码；
  - 扫码完成，等待承运人人脸核验；
  - 承运人已核验，等待承运人确认接收。
- 承运方底部按钮按流程执行：
  - 未扫码时调用微信扫码；
  - 扫码后启动前置摄像头完成人脸核验；
  - 核验完成后确认接收并开始运输。
- 禁止发货方代替承运方确认接收，避免出现越权请求和错误的责任归属。
- 交接完成后显示“交接完成，运输已开始”。
- 将前端生成的动态二维码有效期由 60 秒调整为 300 秒，给真机切换账号和扫码预留足够时间。
- 后端允许指定承运人对已经由本人成功消费的二维码进行幂等重试，用于处理扫码成功但页面因网络中断未跳转的情况。
- 二维码仍然只能由运单指定承运人使用；未消费的过期码、撤销码和其他账号扫描仍会被拒绝。

## 三、完成装箱的实际操作

### 发货方

1. 登录发货方账号。
2. 创建运单并填写样本、收货单位、承运人和预计送达时间。
3. 扫码绑定冷链设备。
4. 点击“执行真实预检”。
5. 温度、箱体状态等预检通过后，点击“完成预检并创建运单”。
6. 进入“发出交接”页，看到“装箱已完成”即表示装箱流程已经完成。
7. 将页面上的动态二维码提供给指定承运人扫描。

### 承运方

1. 使用注册时被运单指定的承运人账号登录。
2. 点击“扫描发货方动态二维码”。
3. 扫描发货方手机上的动态二维码。
4. 按提示使用前置摄像头完成人脸核验。
5. 点击“确认接收并开始运输”。

完成后，后端把运单状态更新为 `in_transit`，责任人切换为承运人。

## 四、测试注意事项

- 动态二维码需要两个登录身份配合测试，建议使用两台手机；也可以由发货方截图后，通过另一台登录承运方账号的手机扫描。
- 承运人必须与创建运单时指定的人员一致，否则后端应拒绝核验。
- 摄像头实时画面需要微信真机调试，微信开发者工具模拟器不能完整支持 `camera` 组件。
- 不建议增加“一键模拟完成交接”，因为这会绕过扫码、人脸和责任人校验，破坏责任追溯的可信性。

## 五、到达验收闭环补全

问题：旧运单可能只有“接收单位”文字，没有 `receiver_user_id`。这种运单可以展示报告，但没有任何真实账号具备签收权限，后端会用 `task not found` 隐藏无权操作。

本次补全：

- 验收页只允许运单指定接收方或管理员执行确认接收、拒收和上传验收证据。
- 未绑定接收账号、当前账号不匹配、尚未完成到达交接时，页面显示具体中文原因，不再直接弹出含糊的 `task not found`。
- 原发货方可在旧运单详情页为“运输中且接收账号为空”的任务补充接收方账号。
- 补录只允许填补空缺，不允许在运输途中替换已经指定的接收人，也不能修改承运人。
- 承运人到达后，从任务详情进入“发起到达交接”，生成 `carrier_to_receiver` 动态二维码。
- 指定接收方扫码并完成人脸核验后确认到达，后端将运单状态更新为 `arrived`。
- 运单进入 `arrived` 后，指定接收方才能在验收页确认接收或拒绝接收。

旧运单恢复顺序：

1. 先注册一个角色为“接收方”的真实账号。
2. 使用原发货方账号打开旧运单，在“补充接收方账号”卡片中完成绑定。
3. 使用承运人账号打开运单，点击“发起到达交接”。
4. 接收方账号扫描动态二维码并完成人脸核验、确认到达。
5. 接收方进入到达验收页，上传证据并确认接收或填写原因后拒收。
